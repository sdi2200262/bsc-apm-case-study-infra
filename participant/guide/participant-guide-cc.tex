\section{Welcome}
\label{sec:welcome}

Thank you for taking part in this research. The study compares two AI-assisted software development frameworks, Agentic Project Management (APM) and GitHub Spec-kit, on a fixed coding task. Your contribution helps build the empirical evidence base for the thesis.

You are not being evaluated. The frameworks are. Whatever you produce during your sessions, including incomplete or non-functional code, is valuable data.

\subsection{Data privacy and anonymity}
\label{sec:privacy}

Submissions are handled with strict confidentiality. No personal identifier is linked to your data. You have been assigned a participant ID (e.g., \texttt{P001}); use it in your submission filenames as described later. AI interaction logs are encrypted with a key held only by the research team before being added to the published research dataset. The dataset's structure is transparent; the contents of your sessions remain private.

By proceeding, you consent to the anonymous collection and use of this data as described.

\subsection{Before you start}
\label{sec:beforestart}

You have been provided separately with:

\begin{itemize}
    \item your participant ID;
    \item your per-session framework assignment (which framework to use in session 1 and which in session 2);
    \item credentials for the Anthropic Claude Max subscription you will use during the sessions.
\end{itemize}

Keep these to hand. They do not appear anywhere in this guide or in the participant package.

Read the official documentation of your assigned framework before each session begins; a short throwaway run on an unrelated repository is recommended for first-time familiarity.

\begin{itemize}
    \item Agentic Project Management (APM): \url{https://agentic-project-management.dev}.
    \item GitHub Spec-kit: \url{https://github.github.io/spec-kit/}.
\end{itemize}

\section{Study overview}
\label{sec:overview}

\subsection{What you do}
\label{sec:whatyoudo}

You will complete the same coding task twice, in two separate three-hour sessions, each using a different framework. The two sessions can run back to back, on the same day, or on different days. They must not overlap, and you must approach the second session as if the first had not happened, working from a fresh checkout of the codebase.

\subsection{Time}
\label{sec:time}

Each session is strictly time-boxed to three hours. Stop at the three-hour mark whether or not the task is complete. Submitting unfinished work is an expected and valid outcome.

\subsection{What you submit}
\label{sec:whatyousubmit}

After each session you produce one zip file containing two artefacts at its root:

\begin{itemize}
    \item \texttt{solution.patch}: a unified diff of your work against a pinned starting commit of the implementation codebase.
    \item \texttt{transcripts/}: a flat directory of the AI interaction logs (one \texttt{.jsonl} file per conversation).
\end{itemize}

The zip filename follows the strict pattern \texttt{\{PID\}\_S\{1\textbar{}2\}\_\{apm\textbar{}speckit\}.zip}, e.g., \texttt{P001\_S1\_apm.zip}.

You also answer a short post-session questionnaire about your experience with the framework, submitted on the same form alongside the zip.

\section{Participant package}
\label{sec:package}

This guide ships inside a participant-package zip alongside the task specification and the helper scripts. Its layout:

\begin{verbatim}
participant-package/
|-- participant-guide-cc.pdf       # this document
|-- task/
|   |-- PRD.md                     # Product Requirements Document
|   |-- PROMPT.md                  # default opening prompt for the AI
|   `-- README.txt                 # one-shot setup notes; delete after use
|-- scripts/
|   |-- list-chats.py              # transcript listing helper
|   |-- collect-chats.py           # transcript collection helper
|   `-- reset-chats.py             # transcript wipe helper
`-- .claude/
    `-- skills/
        `-- bsc-apm-study-helper/  # optional Claude Code skill (see Section 3.1)
            |-- SKILL.md
            `-- references/...
\end{verbatim}

\texttt{PRD.md} is the sole source of truth for what to implement. The three Python scripts under \texttt{scripts/} manage the AI's transcript files; you run them yourself between or after sessions, or you have a Claude Code session with the optional helper skill below loaded run them on your behalf with confirmation. They accept your workspace path as an argument so they can sit anywhere on disk.

\subsection{Optional helper skill}
\label{sec:helperskill}

The package ships an optional Claude Code skill, pre-extracted at \texttt{.claude/skills/bsc-apm-study-helper/}, that can answer logistics questions about this guide: setup, the helper scripts, packaging, the between-sessions reset, cleanup. The skill is project-scoped: Claude Code auto-discovers it only when you open Claude Code from the participant-package directory itself. To use it, open a Claude Code session in the participant-package directory:

\begin{verbatim}
cd path/to/participant-package
claude
\end{verbatim}

You then ask logistics questions in that session. To stop using the skill, simply close that session.

\note{The skill is intentionally project-scoped to the participant-package directory, not user-level. It is therefore not loaded in your task's workspace, only in a Claude Code session opened from the participant-package directory. Do not copy it to \texttt{\textasciitilde/.claude/skills/} or to your workspace's \texttt{.claude/skills/}; doing so would defeat that isolation.}

\warn{The skill is for logistics only. It is instructed to refuse questions about the implementation task or the frameworks themselves and to redirect you to their documentation, but the agent may still slip; if it does, the responsibility to disregard such answers lies with you. Acting on, paraphrasing, or carrying any task or framework content the helper produced into a session contaminates your study data.}

\section{System requirements}
\label{sec:requirements}

\subsection{Operating system}
\label{sec:os}

A Linux environment is required. Two paths are supported:

\begin{itemize}
    \item \textbf{Native Linux} (Ubuntu 22.04 or 24.04, or an equivalent distribution).
    \item \textbf{Linux virtual machine} on a non-Linux host. The virtual machine must satisfy every other requirement in this section, and the work happens entirely inside it: the participant package, the codebase clones, the workspace, and the mock environment all live on the VM filesystem.
\end{itemize}

\textbf{macOS.} Two Homebrew-installable VM tools are recommended, split by host architecture. Both are free, open source, CLI-driven, and bring up an Ubuntu LTS VM in one command. Homebrew (\url{https://brew.sh}) must be present first.

Apple Silicon Macs use Multipass:

\begin{verbatim}
brew install --cask multipass
multipass launch lts --name task --cpus 4 --memory 8G --disk 20G
multipass shell task
\end{verbatim}

Intel Macs use Lima:

\begin{verbatim}
brew install lima
limactl start --name=task --cpus=4 --memory=8 --disk=20 \
    --tty=false template:ubuntu-24.04
limactl shell task
\end{verbatim}

On macOS, if neither Multipass nor Lima works on your host, UTM (\url{https://mac.getutm.app}) is a secondary option: free, open source, GUI-driven. Install Ubuntu 24.04 from the official ISO; setup takes longer than the CLI tools because the Ubuntu installer runs interactively.

\textbf{Windows.} Install WSL2 with an Ubuntu 24.04 distribution following the official Microsoft instructions at \url{https://learn.microsoft.com/en-us/windows/wsl/install}, then follow the native-Linux path inside the WSL2 shell.

\warn{Docker Desktop is not a substitute. The mock environment described in Section~\ref{sec:env} runs Docker Engine \emph{inside} the VM, not on the host.}

\subsection{System resources}
\label{sec:resources}

The Linux environment needs at least 4 vCPUs, 8 GB of RAM, and a 20 GB virtual disk; the launch commands above provision these for VM users. After Docker images are loaded (about 1.6 GB for the openeclass container), at least 5 GB of free disk should remain for the workspace, Docker state, and transient files.

\subsection{Tools and libraries}
\label{sec:tools}

The case-study work needs a container runtime (Docker Engine with Compose v2), a C build chain (\texttt{gcc}, \texttt{make}, \texttt{valgrind}, \texttt{pkg-config}, plus the \texttt{libcurl} and \texttt{libxml2} development headers), two scripting runtimes (Python 3.10 or newer with \texttt{uv}, and Node.js with \texttt{npm}), and a handful of command-line utilities (\texttt{git}, \texttt{curl}, \texttt{tar}, \texttt{openssl}, \texttt{bash} 3.2 or newer, and \texttt{gh}). Install Docker first via the official convenience script:

\begin{verbatim}
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
\end{verbatim}

The new \texttt{docker} group membership takes effect on your next login or after \texttt{newgrp docker}. Install everything else with \texttt{apt} and the official \texttt{uv} installer:

\begin{verbatim}
sudo apt-get update
sudo apt-get install -y \
    build-essential pkg-config valgrind \
    libcurl4-openssl-dev libxml2-dev \
    git curl tar openssl gh python3 python3-pip npm
curl -LsSf https://astral.sh/uv/install.sh | sh
\end{verbatim}

If \texttt{uv --version} reports \texttt{command not found} immediately after the install, run \texttt{source \textasciitilde/.local/bin/env} once or open a new login shell so the installer's PATH update takes effect. The C minimums are \texttt{gcc} 9.0 (for C11), \texttt{libcurl} 7.81.0, and \texttt{libxml2} 2.9.13; Ubuntu 22.04 and 24.04 both satisfy them. Verify the toolchain:

\begin{verbatim}
gcc --version
pkg-config --modversion libcurl
pkg-config --modversion libxml-2.0
valgrind --version
python3 --version
node --version
npm --version
uv --version
\end{verbatim}

\section{AI tools}
\label{sec:aitools}

The session uses a coding-agent CLI (Claude Code) and one of two AI-assisted development frameworks (APM or Spec-kit). The participant package does not bundle any of them. Install Claude Code once before either session, and install the assigned framework's CLI before that session begins. The system requirements in Section~\ref{sec:requirements} cover the underlying tools all three depend on.

\subsection{Claude Code}
\label{sec:aitools:claude}

Install the Claude Code CLI by following the official instructions at \url{https://docs.claude.com/en/docs/claude-code}. Sign in with the credentials you were provided.

\subsection{Agentic Project Management (APM)}
\label{sec:aitools:apm}

APM ships as an npm package; the CLI is invoked as \texttt{apm}.

\begin{verbatim}
sudo npm install -g agentic-pm
apm --version
\end{verbatim}

\subsection{GitHub Spec-kit}
\label{sec:aitools:speckit}

Spec-kit runs through \texttt{uvx} from a release tag of the upstream repository; the CLI is invoked as \texttt{specify}, prefixed by the same \texttt{uvx --from} expression on every invocation. \texttt{v0.8.3} is the floor verified for this study; any newer release tag listed at \url{https://github.com/github/spec-kit/releases} is also acceptable.

\begin{verbatim}
uvx --from git+https://github.com/github/spec-kit.git@v0.8.3 \
    specify --help
\end{verbatim}

\section{Workspace}
\label{sec:workspace}

The participant package's \texttt{task/} directory holds \texttt{PRD.md} (the requirements you implement against), \texttt{PROMPT.md} (the message you give the AI to open the session), and a throwaway \texttt{README.txt} with the clone commands for the two repositories at their pinned commits. The \emph{workspace} is the directory in which you open Claude Code on your Linux environment (native or inside the VM); it is the AI's working directory for the session, and it must end up with this exact layout:

\begin{verbatim}
<workspace>/
|-- PRD.md
|-- PROMPT.md
|-- eclass-mcp-server/      # implementation codebase
`-- openeclass/             # legacy PHP codebase (read-only reference)
\end{verbatim}

Create the workspace as a fresh directory of your choice on the Linux filesystem (\texttt{\textasciitilde/workspace/} is a reasonable default), copy \texttt{PRD.md} and \texttt{PROMPT.md} into it from the participant package's \texttt{task/} directory, and clone the two repositories alongside them following the next subsection. \texttt{README.txt} carries the same clone commands for convenience and has no further role.

\subsection{Cloning the codebases}
\label{sec:cloning}

Clone \texttt{eclass-mcp-server} and check out the pinned commit \texttt{dbd2d16}. This commit is the patch baseline: every diff you submit is computed against it.

\begin{verbatim}
cd <workspace>
git clone https://github.com/sdi2200262/eclass-mcp-server.git
cd eclass-mcp-server
git checkout dbd2d16
uv sync --dev --all-extras
cd ..
\end{verbatim}

Clone \texttt{openeclass} at its pinned commit \texttt{e8b3329}. The AI treats this codebase as a read-only reference; you should not modify it.

\begin{verbatim}
cd <workspace>
git clone https://github.com/gunet/openeclass.git
cd openeclass
git checkout e8b3329
cd ..
\end{verbatim}

\section{Mock environment}
\label{sec:env}

The task integrates with openeclass through a single-sign-on flow, both for the existing Python MCP (Model Context Protocol) server it expands and for the C replica it asks for. The study ships a self-contained \emph{mock environment} that you run locally during each session: a real openeclass instance paired with a mock SSO service whose flow matches \texttt{eclass-mcp-server}'s integration, pre-loaded with a fixed test data set so every participant's session runs against identical state.

\subsection{Download and install}
\label{sec:env:install}

The mock environment ships from the \texttt{sdi2200262/bsc-apm-case-study-env} GitHub repository as two architecture-specific releases, each with a single tarball asset:

\begin{itemize}
    \item Tag \texttt{bsc-apm-case-study-env} ships \texttt{bsc-apm-amd64.tar.gz} for x86\_64 hosts (most Intel and AMD Linux machines, and the Linux VM on an Intel Mac).
    \item Tag \texttt{bsc-apm-case-study-env-arm64} ships \texttt{bsc-apm-arm64.tar.gz} for arm64 hosts (Apple Silicon Macs running a Linux VM, arm64 Linux servers, Raspberry Pi 4/5, etc.).
\end{itemize}

Identify your architecture with \texttt{uname -m}: \texttt{x86\_64} means amd64, \texttt{aarch64} or \texttt{arm64} means arm64. Pick a prefix on disk for the mock environment, separate from your workspace (the rest of this guide writes \texttt{<mock>/} for that path; \texttt{\textasciitilde/.bsc-apm} is a reasonable default). Run \emph{one} of the two download commands below, the one that matches your architecture:

\begin{verbatim}
mkdir -p <mock> && cd <mock>

# x86_64 hosts:
gh release download bsc-apm-case-study-env \
    -R sdi2200262/bsc-apm-case-study-env \
    -p 'bsc-apm-amd64.tar.gz'

# arm64 hosts:
gh release download bsc-apm-case-study-env-arm64 \
    -R sdi2200262/bsc-apm-case-study-env \
    -p 'bsc-apm-arm64.tar.gz'
\end{verbatim}

Then unpack and bring the stack up. \texttt{./install} loads the bundled Docker images, generates self-signed TLS certificates into \texttt{./certs/}, and writes a pre-configured \texttt{.env} alongside. \texttt{./scripts/up} brings the three containers up, performs openeclass's first-time install on first run, and applies the test data; this takes a few minutes on a clean host.

\begin{verbatim}
tar -xzf bsc-apm-*.tar.gz
./install
./scripts/up
\end{verbatim}

The stack listens on two URLs once it is ready:

\begin{itemize}
    \item \texttt{http://localhost:18080/} for the openeclass instance.
    \item \texttt{https://localhost:18443/} for the mock authentication service.
\end{itemize}

Ports 18080 and 18443 must be free on the Linux environment. If another service is bound to either port, stop it before running \texttt{./scripts/up}.

\subsection{Lifecycle commands}
\label{sec:env:lifecycle}

Once installed, manage the environment from its prefix:

\begin{itemize}
    \item \texttt{./scripts/up}: bring the stack up. Idempotent.
    \item \texttt{./scripts/down}: stop the stack; named volumes survive.
    \item \texttt{./scripts/status}: probe each service from the mock side and report whether the stack itself is healthy.
    \item \texttt{./scripts/verify-mcp -{}-mcp-root <path>}: consumer-side complement to \texttt{status}; verifies that an \texttt{eclass-mcp-server} checkout authenticates against the mock with the \texttt{.env} and \texttt{certs/} it has been given. Runs only against the pinned baseline (Section~\ref{sec:cloning}), at initial setup or after a between-sessions reset.
    \item \texttt{./scripts/logs}: tail container logs.
    \item \texttt{./scripts/reset}: drop database state and re-apply the test data.
\end{itemize}

You should not need to reset during a session. If you do (for instance, after a destructive experiment from the AI), \texttt{./scripts/reset} returns the environment to its initial state.

\subsection{MCP server configuration}
\label{sec:env:config}

The \texttt{.env} and \texttt{certs/} that \texttt{./install} wrote are everything the implementation needs to authenticate against the mock. Copy both into the \texttt{eclass-mcp-server/} checkout, preserving the \texttt{certs/} subdirectory:

\begin{verbatim}
cp <mock>/.env <workspace>/eclass-mcp-server/.env
cp -r <mock>/certs <workspace>/eclass-mcp-server/certs
\end{verbatim}

The \texttt{.env} references the certificate by relative path, so no further configuration is required.

\subsection{Uninstall}
\label{sec:env:uninstall}

To remove the mock environment from your machine after the study, stop the stack and drop its volumes (\texttt{down -v}), remove the loaded images, and delete the prefix:

\begin{verbatim}
docker compose -f <mock>/compose.yaml down -v
docker rmi bsc-apm/openeclass:dev bsc-apm/mock-cas:dev
rm -rf <mock>
\end{verbatim}

\section{Session workflow}
\label{sec:workflow}

A session has three phases: starting, working, and wrapping up. Between your two sessions, run the reset at the end of this section to return the workspace and the transcript store to the same state the setup steps above produced for session 1.

\subsection{Starting a session}
\label{sec:starting}

Note the wall-clock start time, then open Claude Code with the workspace as its working directory. Each framework has its own way of starting; follow your assigned framework's documentation and point it at \texttt{PROMPT.md} as the task.

\subsection{Working on the task}
\label{sec:working}

Work for up to three hours and stop at the three-hour mark whether or not you have finished. Use only the framework assigned to your current session and follow its documented workflow as written; the study compares frameworks as documented, not as adapted on the fly. Do not run the participant package's helper scripts during the session, and do not delete any \texttt{.jsonl} file from your workspace's transcript directory; those are your transcripts and are needed in your submission.

\subsection{Wrapping up}
\label{sec:wrapping}

\textbf{1. Create the patch.} From inside the implementation codebase, stage every change (including new files) and diff against the pinned commit. The \texttt{-{}-cached} flag is what pulls newly created source files into the diff, even when the working tree is otherwise clean.

\begin{verbatim}
cd <workspace>/eclass-mcp-server
git add -A
git diff --cached dbd2d16 > ../solution.patch
\end{verbatim}

\textbf{2. Collect the transcripts.} Claude Code stores transcripts under \texttt{\textasciitilde/.claude/projects/} in a per-workspace subdirectory whose name is the workspace's absolute path with every \texttt{/} replaced by \texttt{-}. List what is in your workspace's transcript directory and pick the rows that belong to the session you just finished; the \texttt{-{}-from-projects} flag tells \texttt{list-chats.py} to resolve the mapping for you:

\begin{verbatim}
python3 /path/to/scripts/list-chats.py \
    <workspace> --from-projects
\end{verbatim}

The script prints one row per transcript with first and last record timestamps and a preview of the first user message. Copy the matching rows out with \texttt{collect-chats.py}, pasting the timestamps verbatim into \texttt{-{}-from} and \texttt{-{}-to} (slightly widen the window to be inclusive):

\begin{verbatim}
python3 /path/to/scripts/collect-chats.py <workspace> \
    --from 2026-05-01T09:00 --to 2026-05-01T12:30
\end{verbatim}

The script copies the matching transcripts into \texttt{<workspace>/transcripts/}. Verify the contents of that directory by re-running \texttt{list-chats.py} against it with \texttt{-{}-from-dir}, which scans the directory directly instead of resolving a workspace path:

\begin{verbatim}
python3 /path/to/scripts/list-chats.py \
    <workspace>/transcripts --from-dir
\end{verbatim}

The output should match the rows you intended to collect, with the same first and last timestamps. If a row is missing, widen the time window and re-run \texttt{collect-chats.py}.

\textbf{3. Package the submission.} Zip \texttt{solution.patch} and \texttt{transcripts/} together at the workspace root. The filename uses your participant ID, the session number, and the framework you used in this session:

\begin{verbatim}
cd <workspace>
zip -r P001_S1_apm.zip solution.patch transcripts/
\end{verbatim}

The zip must contain exactly two entries at its root: \texttt{solution.patch} and \texttt{transcripts/}. Files under \texttt{transcripts/} are flat \texttt{.jsonl} files; do not nest them under any subdirectory.

\textbf{4. Move the zip out of the workspace.} The between-sessions reset wipes everything in the workspace, including the zip. Store it in a directory outside the workspace and outside the participant package; \texttt{\textasciitilde/Documents/bsc-apm-submissions/} is a reasonable default. Both session zips end up there, and the cleanup steps later leave that directory untouched.

\begin{verbatim}
mkdir -p ~/Documents/bsc-apm-submissions
mv <workspace>/P001_S1_apm.zip ~/Documents/bsc-apm-submissions/
\end{verbatim}

\textbf{5. Submit the form.} Open the submission form, fill in the per-session questions, and attach the zip you just stored. Do this immediately after wrapping up, while the session is fresh.

\begin{center}
\href{https://forms.gle/yNDWvsBHAHwq8Dks7}{https://forms.gle/yNDWvsBHAHwq8Dks7}
\end{center}

\subsection{Resetting between sessions}
\label{sec:between}

Run this after the first session has wrapped up and before the second session starts. Before running any of the steps below, confirm that session 1's submission zip is in your safe-storage directory (e.g., \texttt{ls -la \textasciitilde/Documents/bsc-apm-submissions/} should list \texttt{P001\_S1\_*.zip}); the reset is destructive and only zips outside the workspace survive. The reset then returns the workspace and the transcript store to the same state the setup steps above produced for session 1, so session 2 begins from an identical baseline. The mock environment is left alone unless you have a reason to believe it has drifted from its initial state.

\textbf{1. Reset the implementation codebase.} From inside \texttt{eclass-mcp-server}, hard-reset to the pinned commit, wipe untracked and ignored files, and rebuild the virtual environment from scratch:

\begin{verbatim}
cd <workspace>/eclass-mcp-server
git reset --hard dbd2d16
git clean -fdx
uv sync --dev --all-extras
\end{verbatim}

\texttt{git clean -fdx} removes every untracked file, including ignored files such as \texttt{.venv/} and any \texttt{\_\_pycache\_\_/} directories. Re-copy \texttt{.env} and \texttt{certs/} from the mock-environment prefix afterwards (Section~\ref{sec:env:config}); they are removed by \texttt{git clean}.

\textbf{2. Reset the reference codebase.} Do the same for \texttt{openeclass}, in case the AI inadvertently modified it:

\begin{verbatim}
cd <workspace>/openeclass
git reset --hard e8b3329
git clean -fdx
\end{verbatim}

\textbf{3. Sweep the workspace.} Confirm the workspace root contains exactly four entries: \texttt{PRD.md}, \texttt{PROMPT.md}, \texttt{eclass-mcp-server/}, and \texttt{openeclass/}.

\begin{verbatim}
ls -la <workspace>
\end{verbatim}

Delete any extra files or directories the AI may have created at the workspace root. If \texttt{PRD.md} or \texttt{PROMPT.md} were modified during the session, restore them from the participant package's \texttt{task/} directory; session 2 must read them in their original form.

\textbf{4. Wipe the transcripts.} Clear the transcript store for this workspace; the script touches only that workspace's transcripts:

\begin{verbatim}
